# 微迹应用检查与完善

2026-10-16，基线 `f3f75bf`（1.7.0），本轮产物 1.7.1（build 16）。从启动与权限、采集、后台任务、数据库、文件/图片、交互、MCP 兼容和打包检查；没有读取真实通知或微信文件内容。

## 已修复的主要问题

| 维度 | 确认的问题 | 本轮处理 |
| --- | --- | --- |
| 界面响应 | 消息和文件查询排在目录扫描、解码之后 | 独立只读查询队列，读取一致快照；图库保留独立只读队列。新档案先初始化，再启动正常读取。 |
| 搜索正确性 | 改变输入后，250 ms 防抖期间旧结果仍能覆盖界面 | 输入变化立即使旧结果失效；取消等待中的重复刷新，只执行同类最新查询，并在主线程交付前再次验证。 |
| 目录生命周期 | 停止监听后，排队扫描仍写索引和回填旧状态 | 目录任务使用共享取消标记；切换目录、清空和退出后取消旧任务，阶段间检查标记。新目录不会显示上一账号的文件、图片或关联。 |
| 图片与采集 | 大批图片解码长时间独占写队列 | 后台预览分成每批最多 5 张、每轮最多 100 次尝试；批次之间让出写队列，采集可执行。可见图片也缩小批次；支持批次间和单图间取消。 |
| 重复采集开销 | 每两秒重新解码全部未变化通知，并逐条进入档案事务 | 有界内存指纹缓存，最多 10,000 个摘要；每轮仍读取系统保留的只读快照并核对数据，不缓存正文。 |
| 缓存正确性 | 简单跳过重复行可能漏掉更新、导入或清空 | 本进程的 ingest/clear 版本、SQLite 其他连接的 data_version、来源路径和逐行指纹共同校验；失败记录重试，比源通知更新的已归档版本不进入复用缓存。 |
| 日志与历史规模 | 空轮次扫描全部已同步事件；新增事件同步时重复更新历史 | 待同步事件使用部分索引，UPDATE 限定 mirrored=0。含 1001 条已同步历史的测试中，新同步一条仅更新一行，空同步无数据写入。 |
| 闲置开销 | 每次轮询都替换状态文件，目录健康时仍每 15 秒全量补扫 | 不变状态约 15 秒合并写入，状态/错误/源数量变化立即写入；定时器增加容差。FSEvents 健康时每分钟补扫，不可用时仍每 15 秒。 |
| 事件持续到达 | 连续变更不断重置防抖，可能一直推迟扫描 | 常规 0.8 秒合并，连续事件最多等待约 2 秒发起扫描；实际执行仍取决于当前后台工作。 |
| 清空与退出 | 旧图片窗口、查询或延后任务仍可能回填；退出时启动任务可能继续调度 | 清空关闭图片并重置展示数据、清理显示缓存；取消旧查询、采集和媒体任务。退出进入统一关闭状态，不再提交新后台工作。 |
| 设置一致性 | 保存失败后界面和运行目录已经改变，重启后又回旧值 | 设置先保存成功再应用；写入失败保留旧开关和目录。档案操作期间阻止重复导入、备份和目录选择。 |
| 错误与加载体验 | 本地档案读取错误被误报为通知权限；非法通知时间可能触发数值转换崩溃；初次空列表误显示“无结果” | 区分本地档案与通知源错误，拒绝非有限/异常时间和空 UUID 误身份，文件和图库使用加载状态。 |

前 3 个问题先用合成测试复现了失败：扫描阻塞查询、搜索旧结果覆盖、停止后仍扫描。修改后同一测试通过。

## 验证

- 新增 15 组原生行为检查，包含队列合并/迟到结果、目录切换/清空/退出、持续事件、预览让出写队列与活动任务取消、设置写入失败、状态写入合并、采集缓存边界/失效/错误重试、非法时间及日志效率。
- 可运行原生回归共 39 组通过，3 个性能基准默认跳过。已有 3 组受锁屏文件保护影响的图片读取检查未计入通过数量。
- 500 条带合成通知元数据的 release 算法对照，完整重放约 24.99 ms，指纹复用约 1.16 ms；未变化轮次的重新解码数 500 → 0。此结果不是整机功耗或真实图片解码性能。详情见 [Performance.md](Performance.md)。
- MCP 的 stdio / HTTP 合成查询流程、真实 HTTP 传输及固定签名在最终产物上复核，记录见 [Validation.md](Validation.md)。

## 仍需继续的部分

- 实机验收：目前 Mac 仍锁屏，原生控件活动状态、键盘/VoiceOver、授权后返回与重启、跨实际升级的 TCC 保留，以及受保护图片读取须解锁验证。不能把模型/离屏测试当成真实窗口点击验证。
- 更细粒度的进度与取消：目录遍历、单次图片解码和大批导入仍有不可中断的阶段。本轮取消在队列入口、扫描阶段、图片之间和批次之间生效，没有强行终止正在执行的文件枚举、SQLite 事务或系统解码器。
- 图片缓存磁盘管理：已有内存预算，但尚无用户可配置的磁盘配额或过期目录回收策略。后续应先测量实际缓存规模，再设计保留/回收规则；本轮不擅自清理现有图片缓存。
- 更大规模的采集：仍读取一次系统保留的通知快照，指纹复用降低重复解码和写事务成本，没有把系统通知库当作完整聊天库。超大快照的内存峰值、导入进度和中途恢复需要单独基准与实现。
